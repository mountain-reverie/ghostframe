# FEC v2 rev 6, step R6-e2: advertised recovery timing, the tile repair budget, the interleaved split — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. One fresh agent per task; the orchestrator checks each task and runs the gates (browserless suites over 3+ seeds, Docker e2e); one Opus review at the end. Steps use `- [ ]`. **Every code block below is a sketch of intent; where prose and a block disagree, the prose wins.**

**Goal:** the client's recovery window stops being two constants and becomes a function of what the server advertises (the block's span `T_adv`, and an RTT hint), so a requested repair row arrives before the client gives up (E11 §10.4: 6 of 8 requests late at i.i.d. 2 %, 39 of 58 under bursts); tile gets a repair budget in bytes; blocks can span a frame as m interleaved GF(2^8) blocks for 150-200 Mbit/s bursty links; the restated E11 criteria are re-measured, with 150 and 200 Mbit/s bursty cells added. Default-on (E13) stays blocked until this lands and the full sweep is re-run.

## Code facts (read from `bf2a7b1c`; `LIB` = `ghostframe-lib/src/transport`, `IB` = `LIB/io_bridge`, `CC` = `ghostframe-client-core/src/fec_rx`, `PR` = `ghostframe-protocol/src/fec`)

- **The window is two constants on each side, pinned by a test.** Client: `CC/blocks.rs` `FEC_RX_DEFAULT_T_ADV_US = 33_000`, `FEC_RX_ALLOWANCE_US = 10_000`, private `WINDOW_US = 43 ms`; `Block::new` sets `close_at = first arrival + WINDOW_US`; `BlockStore::on_timeout` asks for one more row at `close_at` and sets `close_at = now + WINDOW_US`, then `give_up`s (DECLINED). A block does not know its kind. Server: `LIB/fec_tx/block_table.rs` `CLIENT_T_ADV`, `CLIENT_ALLOWANCE`, `CLIENT_WINDOW`, the free functions `tile_deadline` (`last_sent + 2 x CLIENT_WINDOW + srtt + max_ack_delay`), `h264_deadline` (`last_sent + 2 x CLIENT_T_ADV + srtt + max_ack_delay + RAF_ALLOWANCE`), `t_lr_at`, and `TimerKind::offset()` (a constant per timer kind; `timer_valid` recomputes `base + offset` and compares it with the heap key; the test oracle `brute_next_deadline` repeats the formulas). The pin is the test `the_server_and_the_client_agree_on_the_recovery_window` (imports client-core's constants; also asserts `T_MS_MAX + QUEUE_TARGET < T_adv`).
- **The knob's T cap is in two places:** `config.rs` `FecBlockParams::T_MS_MAX = 20` (used by `FecBlockParams::parse` and the warning text of `fec_blocks_from_lookup`) and `LIB/fec_tx/adapt_size.rs` `T_MAX_MS = 20` (ladder: `t_base_ms`, `Ladder::step`).
- **Wire (`PR/frame.rs`):** SOURCE header 9 bytes (`kind, flags, bundle_seq u32, block_id u16, idx`), flags = scheme (low 4 bits, `0x0f`) | LAST `0x80`; **bits 4-6 are rejected by `parse` as `FrameError::ReservedBits`** (test at ~:375 expects `ReservedBits(0x40)`). REPAIR header 11 bytes (`kind, scheme u8, bundle_seq, block_id, k, r, repair_idx`), `scheme` must equal 0. `FEC_RECORDS_HEADROOM = FEC_REPAIR_HEADER_LEN + FEC_SYMBOL_OVERHEAD = 17` caps every record (`Packer::record_limit`), and `BlockBuilder::outgrown_by` / `RepairJob::len` / `Packer::lone_bundle_len` read the header lengths. `SourceFrame::coded_symbol()` is `len | bundle_seq | records`: the flags byte is not part of the parity.
- **Records inside a bundle are whole inner datagrams.** Server to client, a record is routed by `is_tile_datagram` (bit 31 of the first u32) and otherwise is a frame datagram; the only control routes are tile sentinels `(0xFF,0xFF)` frame dimensions and `(0xFE,0xFE)` eviction (registry in `ghostframe-protocol/src/protocol.rs`). `classify_inbound` and its `INBOUND_DISCRIMINATORS` table are client-to-server only.
- **Server block path:** one `BlockBuilder` in `Packer` (`peek`, `add`, `due`, `close`, `first_sealed_at_us`); `Packer::{set_blocks, close_if_due, t_close_at_us, close_for_mtu, close_now, open_block_id, take_closed}`; `IoBridge::process_closed_blocks` sizes `r` per block (`FecAdapt::r_for_block`), queues `RepairJob`s and calls `BlockTable::on_closed`; `service_pending_repairs` builds the `RepairFrame`, admits it as `AdmitClass::Critical`, calls `register_repair`; `blocks_on_declined` closes the packer's open block if it is the declined one (`packer.open_block_id() == Some(block_id)`); `block_rtt()` reads `reliable_emitter.rtt` (`srtt`, `rttvar`, `max_ack_delay`; `has_sample()` exists).
- **Where tile demand is set: nowhere as a rate.** The tile scheduler's only throttle is the byte budget `drain_scheduler_into_quinn(.., budget_bytes)` passes to `scheduler.tick_at_with`, which is `remaining` of `pull_in_priority` in `IB/pacing.rs::pump_admission` (tokens of the admission bucket). The "tile offers 0.8 x cap" of the sweep is `sweep_scene`'s damage window (`Churn::Region`), test code. **Repair rows already precede first sends:** `drain_reliable_emitter` (`IB/emit.rs`) first calls `service_pending_repairs`, and the pump calls `drain_reliable_emitter` before the class loop and after every pull. Tile source and repair draw on one hard bucket (`AdmissionBucket::try_take`, via `admit_one`); H.264 frames are the soft-charged class (`charge`, may go into debt), which is why only H.264 needed E6.
- **Tile repair bytes exceed the planned count overhead.** `process_closed_blocks` sizes `r` in datagrams (`r_cap(k) = ceil(k/4)`, `adapt_size.rs`); every repair payload is padded to the block's longest symbol (`ClosedBlock::symbol_len`). E11 §10.2: tile bytes over `r/k` is 1.2 (1 %) to 1.5 (5 %: 0.442 bytes against 0.290 `r/k`), H.264 about 1.0.
- **Trim:** `adapt_size.rs::DeclinedTrim` (window 256, on above 1 %, off below 0.5 %, only `CloseReason::Declined`), adds 1 above the `ceil(k/4)` cap (the ceiling is `min(32, 255 - k)`). `BlockTable::decline` is the only producer of `CloseReason::Declined`; the table's `on_declined` ignores the DECLINED reason (it is only logged by `handle_status_record`).
- **Congestion gate today:** `dispatch_loss_report_datagram` passes `bwe.standing_queue()` (quinn's smoothed round trip against its 10 s minimum, read at report time) to `FecAdapt::on_report`.
- **Sweep:** `ghostframe-e2e/tests/browserless_fec_adapt.rs`: `Arm`, `Load`, `Loss` (`Clean`, `Iid`, `Ge3`), `Cell`, `SweepRun` (+`read_run`), `verdicts()` (criteria 0-7), `GATED = [0,1,2,4]`, `engage_ms`, `reduced_grid` (H.264 10 Mbit/s, six losses, 3 seeds), `full_grid`, `control_law_sweep`. All four `browserless_fec_*` targets are already in `.github/workflows/e2e.yml` (lines 143-146).
- **The C header is wider than the lib.** `ghostframe-lib/cbindgen.toml` has `parse_deps = true`, `include = ["ghostframe-protocol"]`, `extra_bindings = ["ghostframe-protocol"]`: every `pub const` in `ghostframe-protocol` (23 today in `fec/`) lands in `ghostframe.h`. The lib's own `pub const` do too. The name `QUEUE_TARGET_MS` does not exist: the constant is `admission::QUEUE_TARGET` (a `Duration`, 10 ms).
- **Server `Rtt`** (`block_table.rs`) has `srtt`, `rttvar`, `max_ack_delay` and a `Default` of 50 ms; it has no has-sample flag (`rtt_estimator.rs` has `has_sample()`; `block_rtt()` drops it). `Packer::close_if_due` and `t_close_at_us` read `params.t_ms` of the packer's *current* params, not the block's. `read_run` counts T_lr rows as planned (planned = `block_repairs_sent - request_rows_sent - pto_repair_rows`; T_lr rows go through `next_extra_row` and are in neither subtrahend). `read_run` reads no `TileReady`; those events surface in the harness `framebuffer.rs`.
- **Goldens are PLAIN-only** (`knob_off_sent_frames_match_the_r6c_golden`, `adaptive_with_no_live_params_matches_the_r6c_golden`, `adaptive_after_clean_loss_reports_matches_the_r6c_golden`, `IB/bundle_tx_tests.rs`): no SOURCE or REPAIR frame, so a SOURCE/REPAIR layout change cannot move them. If one moves, something sends a framed bundle on a clean link: stop.
- **Wire crates:** `ghostframe-protocol`, `ghostframe-lib`, `ghostframe-client-core`, `ghostframe-client-wasm`. The wasm crate has no FEC frame code and mirrors no FEC constant (`constants.rs`, `protocol_literals.test.ts` carry none): it needs the target check, not an edit. ## Decisions

**Owner decisions of 2026-11-13 are marked O (fixed, not reopened).** Everything else is a recommendation the tasks build on.

**O1. R6-e2 is in this PR.** S1 (advertised span plus RTT hint) is the core; S2/S3 (interleaved split) follow. **O2. Tile gets a repair budget in this PR** (decision 6 chooses its form). **O3. Criteria (3), (5), (6) are restated** (decision 7; task C0). **O4. E13 (default-on) stays blocked** until this lands, the full E11 sweep is re-run with the 150/200 Mbit/s bursty cells, and the owner agrees.

1. **The wire change (S1).**
   - **SOURCE flags bits 4-6 carry `T_adv`**, a 3-bit code (same value in every source of a block). **REPAIR `scheme` byte: the low nibble is the scheme (must be 0), the high nibble is the RTT hint**, a 4-bit code. Both frames then spend a byte they already have: SOURCE and REPAIR headers keep their lengths (9 and 11), `FEC_RECORDS_HEADROOM` stays 17, `lone_bundle_len` and every byte-count test stay as they are.
   - **Code 0 means "nothing advertised":** span 33 ms (`FEC_RX_DEFAULT_T_ADV_US`), request round 43 ms. A frame without codes behaves as today, which keeps the existing client tests (`WINDOW = 43_000`) as the unadvertised cases.
   - **`T_adv` table (ms) by code 0..7: 33, 10, 15, 20, 25, 40, 50, 66.** The server advertises the smallest entry at least `t_ms + QUEUE_TARGET` (10 ms): the inequality the old cross-crate test asserted (`T + queue < T_adv`) becomes true by construction. T = 5 / 10 / 15 / 20 / 30 / 33 / 50 ms advertise 15 / 20 / 25 / 33 / 40 / 50 / 66. **T = 20 ms (the Wide notch) advertises code 0**, so tests that assert a non-zero code or flip the code must not use it. The block stores both the code and its `t_us` at open (decision 3).
   - **RTT hint (µs) by code 1..15: 4000, 5657, 8000, 11314, 16000, 22627, 32000, 45255, 64000, 90510, 128000, 181019, 256000, 362039, 512000** (x sqrt 2 per step, rounded up when encoding, so the hint is not below the RTT **up to 512 ms**, where code 15 saturates and under-reports longer paths; below that it is at most 1.42 x the RTT plus one step); 0 = unknown. The server sends 0 until `rtt.has_sample()`.
   - **Why the REPAIR header and not a PLAIN record (checked, as asked).** *PLAIN record:* a record is an inner datagram routed by bit 31 of its first u32, else treated as a frame datagram; there is **no free discriminator**. The only room is a third tile sentinel (`(0xFD,0xFD)`), which costs a tile column (ceiling 253 tiles), touches `reassembly.rs`, `drop_plan.rs`, the wasm `constants.rs` and the TS literal test (all four crates plus the web client), and needs a `Packer::lone` flush (pong precedent) that seals the open bundle early every period. *A new REPAIR byte:* header 12, headroom 18, every record limit and golden-with-blocks moves. *The nibble* costs nothing. Coverage: a repair exists in every block with `r >= 1` and every engaged session sends many per second; the client keeps the last hint it saw; a client that has seen none uses the unadvertised round, which only matters for the first block after engaging. The 4-bit log scale gives at most +41 % on the hint (below 512 ms), which delays a decline and never shortens one.
   - **No compatibility, stated:** there is no HELLO bit for this. A client built before S1 rejects a SOURCE with bits 4-6 set (`ReservedBits`) and a REPAIR with a non-zero scheme byte, so the first framed datagram of a block session breaks it. This is accepted (nothing is in production; `project_gpu_first_no_compat`), and deleting `ReservedBits` leaves no wire bit for a later extension: the next one needs a header byte or a version.
   - **`FrameError::ReservedBits` is deleted**: with the span in bits 4-6 and LAST in bit 7 every flags bit is assigned, and a nibble in the scheme byte leaves nothing reserved. A flags byte is invalid only by `UnknownScheme`.
   - **One home for the arithmetic, with no public constant:** a new `ghostframe-protocol/src/fec/timing.rs` keeps the two tables and the numbers (allowance 10 ms, request margin 30 ms, default span 33 ms, H.264 life 66 ms) **private**, and exposes functions only: `t_adv_code_for(span_us)`, `t_adv_us(code)`, `rtt_hint_code_for(rtt_us)`, `rtt_hint_us(code)`, `first_window_us(code)`, `request_round_us(hint_code)`, `h264_skips_request(hint_code)`, and `const fn`s `allowance_us()` and `default_t_adv_us()`. A `pub const` in the protocol crate lands in `ghostframe.h` (code facts); a function does not. Client and server both call it; **the cross-crate mirror test and the `CLIENT_*` constants are deleted, not rewritten** (decision 3). `ghostframe-client-core` keeps its two exported names as `pub const FEC_RX_ALLOWANCE_US: u64 = timing::allowance_us();` (and the default span the same way), and **`blocks.rs` keeps exporting `FEC_RX_ALLOWANCE_US`** because `loss_report.rs` imports it from `super::blocks`. S1 regenerates `ghostframe.h` and `ghostframe_client.h`, commits whatever changed and reviews the diff (expected: nothing).
   - **Margin 30 ms, from data:** E11 §10.4 measured the requested row returning 0.9-7.9 ms after a 43 ms window at a 40 ms round trip under i.i.d. loss, up to 21 ms under bursts; that is 24 ms over the round trip at worst. 30 ms is that plus 25 %. It is a named constant with this derivation; S1b's scene prints the excess and the plan's acceptance bound moves the constant if `late_rows` stays above zero.

2. **What the client does (S1).**
   - **First window = `first_window_us(code)` from the block's first arrival** (`T_adv` + 10 ms allowance), recomputed when a source carrying a code arrives after a repair opened the block (a block not yet requested only). **Request round = `request_round_us(hint)`** (hint + 30 ms; 43 ms with no hint) from the instant the request is sent, then DECLINED. The window is a function of the link: the first part of the block's span, the second of the round trip.
   - **H.264 skip (appendix, kept):** a block holding an H.264 source (**any record of any held source** that is not a tile datagram, bit 31 clear, matching the server's `kind_of`, which calls a bundle H.264 if any record is) is declined at the end of the first window without a request when the hint exceeds `FEC_RX_H264_LIFE_US` (66 ms, two frame intervals at 30 fps, the same two-interval budget `h264_deadline` gives the manager): a row asked for then arrives after the frame is superseded, and declining at once lets the server's manager recover sooner. Hints are codes, so the cut is code >= 10 (RTT above 64 ms). Tile blocks always request. The skip uses the hint, not a clock, and the same function on both sides.
   - **New client counter `late_rows`, counted in blocks:** the first REPAIR row that arrives for a block already given up after it had requested one (the `Closed` marker gains `requested` and `late_counted`, so a second late row of the same block adds nothing). It is the measurement the §10.4 investigation did with temporary instrumentation, and S1b's acceptance reads it.
   - `FEC_RX_MAX_HELD_BYTES` (4 MiB) is not touched here; S3 decides it from a 200 Mbit/s measurement (a frame-spanning block there is about 0.8 MB).

3. **The server's deadlines take the advertised values; the pin goes.**
   - `ClosedBlock` (packer) and `block_table::ClosedBlock` carry the block's `t_adv` code; `block_table::Block` keeps it. Per block: `a = first_window_us(code)`, and `R = request_round_us(H)` where **`H` is the largest hint code the server sent in the last 2 s** (a two-bucket max, 0 before an RTT sample), not the code of the current srtt: the client keeps the last hint it received, which can lag the server's srtt by seconds on a link whose RTT is rising, and a release that used the fresh srtt would fire before a client holding a stale lower hint has finished its round. `Rtt` gains a has-sample flag (`block_rtt()` fills it from `rtt.has_sample()`) so that "R = 43 ms before a sample" is testable.
     - `tile_deadline = last_sent + a + R + srtt + max_ack_delay`.
     - `h264_deadline = last_sent + T_adv + (R - A) + srtt + max_ack_delay + RAF_ALLOWANCE` (A = allowance), which is `tile_deadline - 3 ms` for every code and hint: the old ordering holds by construction (`2A - RAF = 3 ms`).
     - `t_lr_at = last_sent + a + srtt + 2 rttvar`.
     - **With code 0 and no hint all three equal today's values** (86 + srtt, 83 + srtt, 43 + srtt + 2 rttvar): a regression pin that replaces the cross-crate test.
   - `TimerKind::offset()` becomes per block (`offset(&Block)`): TLr and TileRelease `a`, H264Release `T_adv + RAF`; the RTT-dependent `slack()` gains `R` (resp. `R - A`). Keys stay "instant + a block constant", so each per-kind min-heap stays ordered and `timer_valid`'s recompute still matches; `arm`, `timer_valid`, `on_timer` and the test oracle `brute_next_deadline` are updated together; **the oracle computes the formulas from the timing functions' documented values written out in the test, not by calling the production helpers** (otherwise it cannot disagree with them).
   - **`T_MS_MAX` lifts to 50** with `const _: () = assert!(T_MS_MAX as u128 + admission::QUEUE_TARGET.as_millis() <= 66)` (the table's top; `QUEUE_TARGET` is a `Duration`): the knob parser and its warning text follow. **The ladder keeps `T_MAX_MS = 20`** in `adapt_size.rs`: E1 (i) found T = 20 loses nothing measurable against 25-33 ms (107 of 108 comparisons inside the spread at <= 30 Mbit/s, 72 of 72 at 100/200) and cuts tile recovery p95, so the advertised range serves the split (decision 8), not a retune of the narrow and wide notches. The two constants get one comment each saying why they differ.
   - **The advertised span is the block's, not the packer's current knob:** `BlockBuilder::Open` stores `t_us` (and the code) when the block opens; `due()` and `Packer::t_close_at_us` use the stored value. Today both read `self.blocks` at call time, so a block that survives `set_blocks` (the Empty close is skipped while a PLAIN bundle is open: `close_block_on_empty` with no protected bundle) would close on the new `t_ms` while its sources advertise the old span.
   - Memory at 200 Mbit/s is S3's check (decision 2).

4. **DeclinedTrim after S1: a decline of a block whose REPAIR_REQUEST was served is `DeclinedLate`, excluded from the trim whatever the timing.**
   - *Why not a timing rule (rejected, the first draft of this plan):* the measured lateness was 0.9-7.9 ms (i.i.d.), mostly inside `2 rttvar`; `srtt` includes queueing; and "sealed" is not "sent": `service_pending_repairs` seals into `pending_bundles` and quinn's FIFO follows. A threshold on those misclassifies the cases that matter.
   - *Rule (FINDINGS §10.5 (b), server side, no wire change):* `block_table::Block` gets `request_served`, set in `on_request` when it produced at least one `Action::Repair` (a request refused over the cap or malformed does not set it). `decline()` closes with `CloseReason::DeclinedLate` when `request_served`, else `Declined`. `DeclinedLate` counts as declined in every outcome counter (`closed_declined` includes it; `closed_declined_late` is its subset), enters `DeclinedTrim`'s 256-block window as a non-decline, and never raises the trim. Reason: after a request was served, the decline measures the request round (a late row, a lost row, a server turn), which S1 addresses; it is not evidence that the proactive `r` was too small.
   - *Cost of the rule, to be read in the re-run:* a decline after a served request that is a genuine r shortfall is also excluded, so the trim now sees only declines that never reached a request (the H.264 skip, a block whose first window ended with nothing to ask, an unrequested give-up). `closed_declined_late` against `closed_declined` per cell says how much the trim stopped seeing; if the trim goes blind where r is short (saturated bursts), the follow-up is a per-block "rows held at give-up" signal from the client, not a timing guess.
   - *Kept as is:* the trim's +1 above the `ceil(k/4)` cap; criterion (3)'s saturated bar is then "cap plus the trim row" in cells where `trim_steps > 0` (FINDINGS §10.5 (c)), decided from the re-run. §10.5 (a) (clamp the trim to the cap) is not taken: it would disable the trim exactly where the cap binds.

5. **The congestion-gate proposal of §10.5 is deferred, with its reason.**
   - It replaces the estimator's congestion input: LOSS_REPORT only counts losses per interval, so attributing each loss to the queue state **at departure** needs a per-bundle queue flag in the ledger, filled from the ACK-derived one-way-delay excess (acked bundles only, indexed by departure), plus the report's `first_bundle_seq..last_bundle_seq` to map an interval to its flags. That is new plumbing in `record_ack_bwe_samples` and the ledger, and its own measurement design.
   - It targets criteria (1) and (4) at 2 Mbit/s H.264, where the start-up overflows the 150 ms buffer (31-35 real tail drops per run in all arms; with a 1500 ms buffer the same cell drops 0 and passes). The owner's restatement does not include those two, and this PR changes the decline and hand-off numbers any gate measurement would be compared against: stacking it would confound the re-run (one cause per sweep).
   - Instead C0 adds a **deep-buffer 2 Mbit/s cell** to the sweep, which turns finding 1's attribution into a regression test, and the re-run reports (1)/(4) at 2 Mbit/s honestly as before. If the owner wants E13 with that case closed, the gate is the next PR (R6-e3); the design above is its starting point.

6. **The tile repair budget: measure first (TB0), then apply the mechanism the data picks (TB1). Neither (a) nor (b).**
   - **(a), a tile analogue of E6 scaling tile source by 1/(1+rho), has nothing to attach to and changes nothing.** E6 scales an *encoder target* because H.264 frames are soft-charged and nothing else bounds them. Tile source is bounded by the same hard bucket repair draws on; its only rate is the pull budget `remaining` in `pump_admission`, and a stream limited to tokens already splits them as source `R/(1+rho)`, repair the rest. Scaling the pull would also be defeated by the pump's repeated passes and would not change the steady split. The "demand 0.8 x cap" of E11's 5 % cell is the harness's damage window, not a daemon quantity.
   - **(b), admitting repair below source tiles, reverses a deliberate order** (`drain_reliable_emitter`: "repairs that could not go when their block closed go before any new record"). At saturation it starves the rows a block needs inside its window.
   - **What is known:** tile repair bytes exceed the plan. E11-RCA: source 24.6 MB, repair 11.1 MB (0.45) at 5 % on 10 Mbit/s, source goodput 6.6 against 7.7 with the mode off; planned `r/k` 0.29. §10.2 gives bytes over `r/k` of 1.2 (1 %) to 1.5 (5 %) for tile and about 1.0 for H.264. **What is not known** is how the 0.45 divides: `r/k` at actual symbol size (payload padded to the longest symbol of a block of mixed-size tile bundles), the extra rows (REQUEST, PTO and T_lr, at most `r + 4` per block, which `read_run` counts as *planned* because T_lr rows are in neither of its two subtrahends), headers (11 B a row), and the trim's +1 above the cap. E10's RCA did this breakdown for H.264 and found the trim alone 2.6-7.4 points; nobody did it for tile. A mechanism chosen before the split is a guess, so TB0 measures.
   - **TB1's candidates, chosen by TB0's table:**
     1. *A byte cap on `r`, tile blocks only.* `r <= max(1, ceil(sum(len_i) / (4 x max(len_i))))`, computed in integers as `(sum + 4 max - 1) / (4 max)`, applied **after `r_for_paced`** (the step limit in `RSizer::r_for_paced` is keyed on `k` alone, so a cap applied before it would be undone by a slot written for another block of the same `k`), and only for a block whose `ClosedBlock.kinds` are all `Tile` (a block with any H.264 source keeps the count cap, so H.264 is untouched by construction). Its real bound is `0.25 + 1/k_eff` of source bytes (the ceiling), plus the trim row where the trim is on; it is **not** a hard 25 %. For equal-length symbols it equals the count cap.
     2. *A budget on the extra rows* (request, PTO, T_lr) of tile blocks, if TB0 shows them dominant.
     3. *The trim's interaction* (the +1 above the cap on tile blocks), if TB0 shows it dominant.
   - **The 7.8 Mbit/s arithmetic of the first draft is withdrawn.** With a repair share `rho = 0.25 + 1/k_eff + extras`, source goodput is `R / (1 + rho)`: about 7.4 Mbit/s at `k_eff` 15 and no extras, below the control's 7.7. The cap can close part of the 1.1 Mbit/s gap, not all; TB1's test is a measured reduction and the restated criterion (6), not a predicted number.
