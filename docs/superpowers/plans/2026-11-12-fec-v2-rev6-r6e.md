## Decisions fixed by this plan

**Owner decisions are marked O.** Everything else is a recommendation the plan builds on; the owner may override it without reshaping the tasks.

1. **Modes and default (O1).** `GHOSTFRAME_FEC_BLOCKS` takes `off`, `k_max,t_ms,r` (fixed, as in R6-d) or `adaptive`. The config type becomes `FecMode::{Off, Fixed(FecBlockParams), Adaptive}`.
   - **Recommendation (pending the owner): the daemon default becomes `Adaptive`, in its own last commit (E13), only after the floor, congestion-gate and per-guard fixes of this plan are in (decisions 2, 4, 5) and the sweep (E11) passes, including its 0.01 % cell and the 5 % i.i.d. not-gated control.** On a clean link adaptive sends exactly what the knob off sends (r = 0, PLAIN), and E5 asserts that as a byte-identity test against the R6-c golden; that is the argument for default-on. `off` stays an explicit switch for support.
   - **Needs the owner:** R6-d left the default off "until R6-e". Default-on changes what every session sends once loss appears, and it is the first time the repair path runs in production.
   - The harness default stays `Off` unless a scene or the environment says otherwise, so the existing browserless suites keep their baselines (E13).
2. **"Machinery on" and "live parameters" are two things.** R6-d used `Option<FecBlockParams>` for both. Adaptive needs the table, the packer and the ACK hooks live while the current state is r = 0 (PLAIN). E2 splits them: `fec_mode` (machinery, fixed for the process) and `fec_live: Option<FecBlockParams>` (what the packer and `process_closed_blocks` use now; `None` = PLAIN). **The guards are not all the same kind; E2 classifies each by name** (line numbers at `9b5ab9a7`):
   - **Follow the LIVE params:** `probe_bundle_kind` (`IB/block_tx.rs:88`: a probe-tagged first send is a lone SOURCE only while blocks are live, else PLAIN, or the cluster's byte count drifts by 4 bytes per packet); the close-on-Empty branch of `pump_admission` (`IB/pacing.rs:366`: with live `None` the pump takes the `flush_bundles` branch, never `close_block_on_empty`); `process_closed_blocks` (`block_tx.rs:116`, reads `r`).
   - **Follow the MACHINERY (they must keep working while live is `None`, because blocks and repairs sent earlier are still outstanding):** `blocks_on_arrivals`, `blocks_on_recovered`, `blocks_on_declined`, `blocks_on_repair_request` and `service_blocks` (`block_tx.rs:299, 311, 325, 345, 454`); the TILE_NACK `tile_protected` check (`IB/ack_dispatch.rs:675`); the `fec v2` log block (`IB/frame.rs:2596`). In the pump tail, `service_pending_repairs` runs under machinery even on the `flush_bundles` branch (a repair queued before the switch to r = 0 must still leave).
   - **A change of live parameters is applied at a block boundary:** close the open block with the old parameters (`close_now` then `process_closed_blocks`, so `r` is still readable), then set the new ones. Setting `None` first would drop the open block's repairs (the `let Some(params) = ... else return`).
3. **Inputs (what the controller reads).** Per LOSS_REPORT: `received`, `lost_pre_fec` (loss rate p = lost / (received + lost), over all datagrams, repairs included), `loss_run_hist` (burst length), `interval_ms`, `blocks_unrecoverable` (blocks closed short). Server side: the block table's close outcomes (closed `Accounted` against `Declined` / `HandedOff` / `TimedOut`, already counted), the measured mean `k` of closed blocks (`block_tx.k_sum`), smoothed RTT, the source-bundle rate, `bwe.standing_queue()` and `loss_state.is_limited()` (the two the rate path already reads), and the H.264 frame rate.
   - Not read: `residual_lost`, `repair_wasted` (padding repairs and extra rows make it meaningless as an over-protection signal, decision 8), and any field the client leaves 0.
4. **Estimator.** Two decayed accumulators, `lost` and `total`, per report: `d = exp(-max(n / W, dt / tau))` with `W = 10 000` datagrams and `tau = 10 s` (a window of 1 000 flapped at 100 Mbit/s, where it is under 0.1 s of traffic), then `lost = d * lost + new_lost`, `total = d * total + n`; `p_hat = lost / total`. Attack is instant (counts add), release is the decay. The burst estimate is the same accumulation over the run histogram with bucket representatives 1, 2, 3, 4, 6.5, 12.5, 24.5, 40: `b_hat = lost / runs`. These constants are starting values; E1 and E11 check them, they are `pub(crate) const`s with a comment each.
   - **Congestion versus random loss** (rev 5 §4.3 step 5): an interval is *congested* only when the delay signal says so: `bwe.standing_queue()` holds. A congested interval adds its datagrams to `total` but its losses to nothing (counted `adapt_congestion_skips`). **Not quinn's `congestion_events`, alone or as a qualifier**: under Cubic it is loss by another name; it rose on nearly every report at 5 % i.i.d. loss (measured, R6-e E5), so gating on it never engaged. A rise that coincides with the standing queue adds nothing, the queue already gates. On a policed, shallow-buffer link the loss looks random; goog_cc's loss-based estimator lowers the rate there and E6 makes the encoder pay for the repair overhead, so engaging FEC there is acceptable. **Not `loss_state.is_limited()`** either: goog_cc is loss-limited under plain random loss too. E7 asserts that 5 % i.i.d. loss engages with congestion events rising. Known limit: at a tail-drop bottleneck the queue has often drained when the loss is reported, so only the intervals that still see the queue are gated.
5. **The floor and its hysteresis (O: owner decided 0.1 %, §8 item 5).** r = 0 (PLAIN) while the loss is not shown to be at or above `FEC_LOSS_FLOOR = 0.001`. A bare `p_hat >= floor` flaps: at a stationary 0.1 % the estimate straddles the line, and a lone loss in a young estimate reads as 2 %. So the test is statistical, on the decayed counts `L = lost`, `N = total`:
   - **Engage** when `L >= 3` **and** a one-sided 95 % confidence *lower* bound of the loss rate is at or above the floor (Poisson form: `(L - 1.64 sqrt(L)) / N >= floor`). At `N = 10 000` that needs about 17 losses (0.17 %); at 5 % it passes in the first report. A lone stray loss never engages.
   - **Release** when the *upper* bound (`(L + 1.64 sqrt(L + 1) + 1) / N`) is below the floor **and** `FEC_ADAPT_MIN_DWELL = 5 s` has passed since the last change. The two bounds do not overlap, so a stationary rate near the floor changes state rarely; it cannot flap on one loss.
   - A true 0.1 % link therefore sits mostly in r = 0 and engages only when a run of losses shows the rate is above the floor; the cost is slower engagement at low loss (up to the window), which is the intent of a floor.
   - E3 tests the properties (below); E11 has a 0.01 % cell (must never engage) and checks at most 2 changes per minute at a stationary 0.1 %. The floor is a named const with the owner's decision in its comment.
6. **Control law: widen first, then add parity.** Each evaluation (on every LOSS_REPORT, at most once per 250 ms) yields `(k_max, T)` and an `r_for(k)` policy.
   - **Span (rev 6 §5), from `FINDINGS.md` §8:** two notches keyed on `b_hat`, hysteresis up above 1.5 and down below 1.25, one change per `FEC_ADAPT_NOTCH_DWELL = 1 s`.
     - `b_hat <= 1.5`: `(T_base, k_max 64)` with `T_base = min(max(5 ms, 6 slots), 20 ms)` (a slot is `max_dg` at the source rate).
     - `b_hat > 1.5`: `T = 20 ms` and `k_max` = the bundles in 20 ms at the source rate, clamped to `[64, 223]`.
     - **There is no 10 ms notch**: it is never the unique best in the data and the plan does not keep it. **Loss level `p` moves `r`, not the notch**: no cell shows `p` changing which notch wins at fixed burst.
     - **`T` never exceeds `FecBlockParams::T_MS_MAX` (20 ms) in R6-e**, because the client's window is the constant 43 ms. E1 found that T = 20 loses nothing measurable against 25 / 28 / 33 ms (107 of 108 comparisons at <= 30 Mbit/s and 72 of 72 at 100 / 200 Mbit/s are inside the seed spread) and cuts tile recovery p95; the price is +5 to +7 points of overhead at 2 Mbit/s (10 seeds) and 0 to +2 at 10 Mbit/s.
   - **Parity (rev 6 §5, first-shot sizing):** `r_for(k)` is the smallest `r >= 1` (cap 32, and `r <= max(1, ceil(0.25 k))` **for every k, with no exception for small k**: a lift for `k < 4` makes r non-monotone, k = 3 asks r = 9 where k = 4 asks 1, and costs 40 to 117 % overhead at 2 Mbit/s for no late-frame gain, `FINDINGS.md` §8) such that P(more than r of the k + r datagrams of a block are lost) is at most `FEC_ADAPT_TARGET = 1e-3`, under the fitted model: i.i.d. with `p_hat` when `b_hat <= 1.05`, else two-state Gilbert-Elliott fitted from `(p_hat, b_hat)` (loss 1 in the bad state, mean bad run `b_hat`). `r` is chosen **per block at close from its actual k**, so a 3-source block at low rate gets r = 1 and a 64-source block at 5 % i.i.d. loss gets 11.
   - **`saturated`:** under the cap the 1e-3 target is unreachable for bursty loss (burst >= 3 at k <= 64, and burst 8 at every k, `FINDINGS.md` §8). `r_for` then returns the cap and reports `saturated = true`. Saturation is a state of the link, not a failure of the controller: it is counted (`adapt_saturated`, the share of closed blocks sized at the cap), shown on the log line, and E11's criteria use it instead of reading a missed target as a defect. The tail is an exact dynamic program over the block's positions (no table to regenerate), memoised per quantised `(p_hat, b_hat, k)` and cleared when the quantised pair moves.
   - **Step limits:** the estimator already attacks instantly and releases slowly; on top, `r_for` output for a given k may fall by at most 1 per `FEC_ADAPT_NOTCH_DWELL`. Nothing limits a rise.
   - **Closed-loop trim:** if more than 1 % of the last 256 closed blocks ended `Declined` (`CloseReason::Declined`, the client giving up), add 1 to `r_for` (cap 32) until the share is back under 0.5 %. **Only `Declined`**: a `HandedOff` is often a table cap eviction (`FEC_TX_MAX_BLOCKS`, `FEC_TX_MAX_CACHED_BYTES`) and a `TimedOut` an alarm that must stay 0, neither says r was too small. A window under 256 is too noisy to hold a 1 % threshold. This catches a mis-fitted burst model without trusting `residual_lost`.
7. **Overhead and the encoder target.** The H.264 media target becomes `RATE_SHARE x estimate / (1 + rho)` where `rho` is the planned overhead (EWMA of repair bytes over source bytes, 0 when r = 0). Without this, a 25 % overhead on top of 0.8 x estimate spends 1.0 of the grant and the ceiling reads saturation.
   - **Do not divide the estimate before `step_in_place`.** The policy would read the engagement of FEC as a fall of the estimate: it can release a held spike (`spike_releases`), and a fall of more than 30 % is a `cut`, which sets `last_cut_at` and blocks padding and the probe raise (`h264_cut_recent`) for `PAD_QUIET_AFTER_CUT`.
   - **Scale the policy output instead.** `RatePolicy` keeps its spike, cut and dead-band logic in unscaled units; a new `media_scale = 1 / (1 + rho)` multiplies only the `bps` it emits (`RateApply.bps`). A change of `media_scale` beyond the 10 % band, with the unscaled candidate unchanged, produces an apply with `cut = false`, subject to the 250 ms `APPLY_MIN_INTERVAL`, and touches neither the spike state nor `last_cut_at`. `rho` is smoothed (EWMA) so it moves slowly.
   - The compile-time assert `RATE_SHARE < SATURATION` is restated for the media share plus repairs (`RATE_SHARE` is the total share the stream may spend, repairs included); it is not deleted. E6 proves it with a capacity scene and a no-cut test.
8. **Padding as repair (rev 6 §5.1), and what it can and cannot do.**
   - **Where it applies:** only while the live state is r >= 1 and a block can still take a row (`Phase::Repair`, symbols held). Otherwise padding stays what it is (PLAIN copies of an acknowledged fragment), so a clean link and the knob off stay byte-identical (the golden scene contains a pad).
   - **Which block (finding, differs from §5.1's wording):** at frame time the frame's own fragments are only queued, not sealed, so their block cannot take rows yet; the previous frame's blocks are usually already `Accounted` and freed at RTT < ~30 ms. So the useful block is **the frame's own, at its close**: when a block closes while a probe window is open and short, the window's shortfall is paid with extra rows of that block (rows `r..`), and anything the row cap leaves goes out as PLAIN filler. `h264_probe_pad` therefore reserves the expected repair bytes (as it already does for `expected_later`) instead of queueing them.
   - **Row budget:** pad rows are their own budget per block, `FEC_PAD_ROWS_PER_BLOCK = max(r, 4)`, apart from the `r + 4` cap on requested / PTO / `T_lr` rows (a hostile client cannot reach it), and never above `255 - k`; rows are never reused.
   - **Accounting that must hold:**
     - `probe_padding_bytes` stays wire bytes: a repair pad is `RepairJob::len()` (its REPAIR frame), the same unit as `lone_bundle_len` for a copy. New subset counters `probe_padding_repair_datagrams` / `_bytes` say how much of it was repair.
     - **`bytes_sent_before` must be monotone in send order.** A pad row's tag is assigned when the row is admitted, not when the shortfall is computed; the reservation must not advance `p.bytes_sent` (otherwise later tags run ahead of the packets that carry them, and the estimator's send rate skews silently).
     - goog_cc sees one packet of the REPAIR frame's size with its `PacedPacketInfo`; the acked-rate window is 300 ms and counts every acknowledged byte, repairs included. A lost repair is fed untagged like any loss; a lost *pad* repair pauses the raise like a lost pad copy (`pads_lost` extends to it).
     - The tag lookup today needs a record; a repair bundle has none. E9 adds a bounded `bundle_seq -> ProbeTag` map for pad repairs (cap `PAD_RING_CAP`) consulted when `tx.records` is empty. It must not share the pad ring's key space (`wire_seq`).
     - The ALR / probe-raise guards (`h264_pad_allowed`, `h264_cut_recent`, a lost raised frame or pad) apply unchanged to repair pads.
   - **Value gate (O3, recommendation pending the owner):** a repair pad helps only when its block lost more than r. E10 measures it as an A/B (E9's behaviour off against on). **If the benefit is zero or inside the seed spread, delete the padding-as-repair code (E8, E9) rather than leave it gated by a const**; dead gated code is the kind of thing this repo has paid for. The plan does not assume the benefit.
9. **The interleaved split above ~70 Mbit/s (§8.1, decided "(a)") and the `T_adv` wire change are not in this PR (O2, recommendation pending the owner).** The split is R6-e's by scope, but a block spanning a frame (33 ms) cannot ride the constant 43 ms client window, so it needs `T_adv` on the wire, and the packer needs m open blocks at once. S1-S3 are moved to the appendix, "follow-up PR (R6-e2)".
   - **Why a follow-up is safe, and where it stops being (E1, `FINDINGS.md` §8 iv):** `T` never exceeds 20 ms here (decision 6), so no wire change is needed. One capped block (k_max 223, 15-17 % overhead) is within the seed spread of the interleaved split at 100 Mbit/s. **At 200 Mbit/s under burst 8 it is not: 3.5 points more late frames (h264; the mix gap of 1.4-2.3 points is inside the spread) at a higher overhead.** So the follow-up is justified for links of about 150-200 Mbit/s and above with bursty loss, not below. 150 Mbit/s was not measured.
   - The owner already decided the split's design (interleaved, m = ceil((k + R)/256), bundle i to block i mod m, r = ceil(R/m)); only the timing is open.
10. **Not in R6-e.** Removing H.264 retransmission (R6-f, on LOSS_REPORT data after this); making the client report the 0 fields (`src_lost_pre_fec`, `recovery_p95_ms`, ...); the rAF batching floor; protecting frame dimensions.

### Task E1: simulation: the T cap, the ladder, split or not; exact tail oracle (model: **sonnet**)

Files: `docs/specs/fec-v2/sim-rev6/adapt_sim.py` (new, imports `uniform_sim.py`; `python3 -I`), `adapt_oracle.py` (new), `adapt_oracle_vectors.csv` (new), `FINDINGS.md` (a new last section). No Rust.

## Appendix (follow-up PR R6-e2, not part of R6-e): advertised recovery timing, and the interleaved split

Recommendation pending the owner (O2): do this as the follow-up. The owner may instead pull it into R6-e; the tasks below then run after E10 and before E11, and E11's grid gains the 200 Mbit/s bursty cells.

**Why.** E1 justifies the split for about 150-200 Mbit/s and above under bursts (decision 9). It also exposes a deeper limit: the client's recovery timing is two fixed constants, a 43 ms repair wait from a block's first arrival (`FEC_RX_DEFAULT_T_ADV_US` + `FEC_RX_ALLOWANCE_US`) and a request round that assumes nothing about RTT, pinned to the server by `CLIENT_T_ADV` / `CLIENT_WINDOW` and a cross-crate constant test. A frame-spanning block, a long-RTT path and a frame that cannot be repaired in time all need the client to know more.

**What the server advertises.**
- **The block's span `T_adv`**, in SOURCE flags bits 4-6 (3 bits). **Code 0 means 33 ms, the client's fallback `FEC_RX_DEFAULT_T_ADV_US`** (an unmarked frame behaves as today); 1..7 are 40, 50, 66, 100, 150, 200, 250 ms or whatever E1's data asks for. Every source of the block carries it, so the client learns it from the first arrival with no extra channel and no loss exposure. It relaxes today's `ReservedBits` rejection (`ghostframe-protocol/src/fec/frame.rs:100-106`); the protocol test at `frame.rs:375`, which expects `ReservedBits(0x40)`, changes with it (a still-undefined case takes its place).
- **An RTT hint**, so the client does not guess the request round. The SOURCE flags have no room left, so the carrier is the REPAIR header or a periodic PLAIN record; the follow-up's first step checks which fits and whether a free record discriminator exists. The server sends its smoothed RTT quantised (for example 4 ms steps, 8 bits).
- **What the client derives:** its **repair wait** = block span + jitter allowance (replacing the fixed 33 + 10 ms window), and its **REPAIR_REQUEST round** = about RTT + margin before it declines. **For H.264 it skips the request when the RTT exceeds the frame's useful life** (the repair could not arrive before the frame is superseded or a recovery is planned) and declines at once, so the server's manager recovers sooner.
- **What it replaces:** the fixed 43 ms windows and the cross-crate constant pin (`CLIENT_T_ADV`, `CLIENT_WINDOW`, the lib test that mirrors client-core's constants). The server's deadlines (`tile_deadline`, `h264_deadline`) take the advertised values. The knob's `T_MS_MAX = 20` limit lifts to the advertised range.
