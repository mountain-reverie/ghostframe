# M3.6 — Dynamic Mode-Switch Policy (Bandwidth/Latency-Aware Lossless Strategy)

**Date:** 2026-06-03
**Status:** Design approved

## Context

After M3.5 the classifier picks H264-full-frame vs TileCodec from **static** cost numbers: a single hard-coded `bytes_per_us = 12.5` (≈100 Mbps), fixed encode µs per codec, fixed `refinement_bandwidth_fraction = 0.2`. The bench-tuned constants are correct only for the bandwidth point they were calibrated against. In production the client's link can be 10 Mbps DSL or 1 Gbps LAN, can drop datagrams under congestion, can stall on suspension, and the server has no way to discover any of that today.

The classifier already has the right *shape* — it compares "all-tile-codec µs" against "h264-frame µs" plus their respective bytes-per-µs costs. What it's missing is a live `bytes_per_us` input and a way to bias the cost toward refinement when bandwidth headroom exists, away when it doesn't.

`ReceiverFeedback` (`transport/feedback.rs`) is already wire-decoded by `io_bridge::dispatch_feedback_bytes` — its `loss_rate()`, `datagrams_received`, and `suspension_detected` are consumed today only by `update_fec_from_feedback` for FEC parity tuning. The classifier never sees it.

`Scheduler::refinement_bandwidth_fraction` self-adapts (halve on low delivery, double on high) inside the refinement loop. M3.6 leaves that inner-loop adaptation alone; it operates *one layer up* — at the H264-vs-TileCodec decision and the "should we be opportunistically refining at all right now" question.

**Goal (Objective A).** Maximize wall-clock time spent at PixelPerfect on idle content, with graceful degradation to "B-grade" (visually lossless but not bit-exact, ≥ 0.98 SSIM) when bandwidth or loss force a trade.

**Goal (Objective B, derived).** Never starve newly-dirty tiles to feed refinement. The user-visible "what changed in the last frame" channel is sacred; refinement is the background process.

**Non-goal.** Per-tile H264 was dropped in practice (alongside BC1); M3.6 does not re-open that lever. The toolbox is exactly `{H264-full-frame, Solid, PalRle, Cdf53}` plus the Cdf53 refinement pass schedule.

## Architecture

### Three phases (a + b + c)

Mirrors M3.3 and M3.5 cadence: each phase reviewable as one PR with one focused concern.

**M3.6a — Signal plumbing.** Lands the wiring with no behavioral change. `ReceiverFeedback` consumed by classifier via a new `AdaptationContext` struct; QUIC `path_stats` (cwnd, smoothed RTT) sampled at the same cadence; smoothed estimates fed through `Classifier::set_bytes_per_us`. Policy still uses the same comparison logic — the *input* is dynamic but the *decision rule* is identical. Existing e2e behavior unchanged; a single new lib unit test asserts that the plumbed value matches what the existing code already reads via `bytes_per_us()`.

**M3.6b — Policy refactor.** Adds a refinement-deficit bias to the existing cost comparison (lean toward TileCodec+refinement when bandwidth headroom + PixelPerfect deficit both present; lean toward H264 when loss/RTT spike or refinement queue starves dirty-tile budget). Headroom guard: hard-trigger H264 escalation if `bytes_per_us < HEADROOM_MIN_BYTES_PER_US`. Loss override: hard-trigger H264 if smoothed loss rate > `LOSS_OVERRIDE_THRESHOLD`. Hysteresis re-anchored to "consecutive seconds above/below threshold" rather than frame count, so it scales with capture rate. Behavioral tests (new `e2e_bandwidth_cap_*` family) replace existing brittle constant-threshold assertions.

**M3.6c — Tuning + observability.** Runs the M3.5 bench across three bandwidth points (10 / 30 / 100 Mbps, simulated via new `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP` env-var), retunes the three new constants from the matrix, lands one new `mode.decision` telemetry event per mode change with the signal vector that triggered it, and updates `docs/specs/m3-codec-bench-results.md` with a new "M3.6 dynamic-policy" section. No production code changes after this phase — it's the tuning + audit-trail close-out.

### Why "bias the existing cost comparison" instead of a new state machine

The current classifier (`tile/classifier.rs:Classifier::decide`) already does the right thing structurally: it weighs full-frame H264 against the sum of per-tile codec costs, where each cost is `encode_us + bytes/bytes_per_us`. Making `bytes_per_us` dynamic + adding a small bias term to favor refinement when headroom permits is a *targeted* change to a function that already has good shape. A state machine (decision register D6, the rejected D upgrade path) would be more legible but requires re-validating every existing classifier proptest and rewriting the cost-comparison-grounded e2e tests; M3.5b just retuned this surface.

The D upgrade path stays spec'd: if M3.6b's biased cost approach produces visible thrashing in M3.6c's bench, M3.6 reopens with a state-machine refactor as M3.6d. This decision is *re-litigated* by data, not relitigated by intuition.

### Signals: hybrid QUIC + ReceiverFeedback

Two complementary signal sources. Neither alone is sufficient.

**QUIC `path_stats`** (cwnd, smoothed_rtt, lost_packets accumulator) — read from the quinn `Connection` once per server tick. Cwnd × inverse-RTT gives an upper-bound on sustainable throughput. Slow-start at session open means early values undershoot — the classifier *already* starts in H264 mode, so undershoot is safe: it just keeps H264 on a bit longer until cwnd opens up. No new wire bytes.

**`ReceiverFeedback`** (existing, 100ms cadence) — `loss_rate()` and `suspension_detected` flag. Where QUIC sees retransmits as "we recovered", the receiver-side counters see datagram drops as the user does (we don't retransmit datagrams). Smoothed over the last 5 feedback windows (≈ 500 ms) so a single jittery sample doesn't flap the policy.

The two get combined in `AdaptationContext`:

```rust
// ghostframe-lib/src/tile/classifier.rs (new)
#[derive(Debug, Clone, Copy, Default)]
pub struct AdaptationContext {
    /// Smoothed throughput estimate, bytes per µs.
    /// Sourced from min(cwnd/rtt, recent_emit_bytes/window).
    pub bytes_per_us: f32,

    /// Smoothed one-way RTT, µs. Sourced from QUIC `path_stats`.
    pub smoothed_rtt_us: f32,

    /// Smoothed datagram loss rate over last 5 ReceiverFeedback windows.
    pub loss_rate: f32,

    /// Last ReceiverFeedback's suspension flag, OR'd across last 2 windows
    /// to debounce single-window flaps.
    pub suspended: bool,

    /// Monotonic counter incremented on each AdaptationContext update.
    /// Used by tests to assert "classifier saw the new value before
    /// making decision N".
    pub last_update_seq: u32,
}

impl Classifier {
    pub fn set_adaptation_context(&mut self, ctx: AdaptationContext);
}
```

`AdaptationContext` is owned by `io_bridge`'s `BridgeState` and pushed to the classifier each time either a `ReceiverFeedback` arrives or the server's per-tick QUIC poll fires (whichever is sooner). The existing `Classifier::set_bytes_per_us` accessor becomes one slice of `set_adaptation_context`.

### Refinement-deficit bias term

Today's cost comparison (`tile/classifier.rs:decide`):

```text
all_tile_codec_us = sum(encode_us[t] + bytes[t]/bytes_per_us)
h264_us           = h264_frame_us + h264_frame_bytes/bytes_per_us
choose H264 iff h264_us < all_tile_codec_us
```

M3.6b extends this to:

```text
refinement_deficit_tiles = count(t in active_tiles where t.passes_done < CDF53_PASS_COUNT)
refinement_bias_us       = refinement_deficit_tiles * REFINEMENT_BIAS_PER_TILE_US
choose H264 iff (h264_us < all_tile_codec_us + refinement_bias_us)
              OR  (bytes_per_us < HEADROOM_MIN_BYTES_PER_US)         // hard override
              OR  (loss_rate > LOSS_OVERRIDE_THRESHOLD)              // hard override
              OR  (suspended)                                         // hard override
```

The bias subtracts (effectively) µs from the tile-codec cost proportional to how much PixelPerfect work is in flight — biasing the decision toward keeping TileCodec on so refinement can complete. The bias is *added to* the H264 comparand (equivalent), which keeps cost comparisons monotonic. When all tiles are at full passes, the bias is zero and the comparison reverts to the M3.5 rule.

Three constants, all initial values to retune in M3.6c:

```rust
// ghostframe-lib/src/tile/classifier.rs
pub const REFINEMENT_BIAS_PER_TILE_US: f32 = 5.0;
pub const HEADROOM_MIN_BYTES_PER_US: f32 = 0.25;       // ≈ 2 Mbps floor
pub const LOSS_OVERRIDE_THRESHOLD: f32 = 0.10;         // 10 % datagram loss
```

### Startup: still H264 first

The bandwidth-discovery cold-start problem (no `bytes_per_us` estimate at session open) is solved by *not changing the startup behavior*. The classifier still picks H264 for the first scene by virtue of its full-frame motion cost being cheap relative to dirty-everything tile-codec cost. As QUIC's cwnd opens and the first `ReceiverFeedback` arrives, `AdaptationContext` becomes populated and the comparison shifts naturally. No explicit "warm-up phase" timer — it's emergent from the cost comparison + cwnd's own slow-start.

The implication for e2e: tests that today rely on hard-coded "H264 for first N frames then switch" assertions will need to assert behavioral outcomes (e.g. "ended in TileCodec within X seconds") rather than counting initial H264 frames. M3.6b's task list explicitly enumerates the e2e tests that need this adjustment.

### Hysteresis re-anchoring

Today `tile/classifier.rs` uses `hysteresis_frames: u32`. That's wrong dimensionally — at 60 fps, `5 frames` is ~83 ms; at 30 fps it's 167 ms; at 10 fps (idle) it's 500 ms. Mode-switch dwell should be wall-clock, not frame-count. M3.6b switches to `hysteresis_micros: u64` and converts the existing default proportionally. Behavioral tests change one line; lib unit tests adjust the same way.

## Phase M3.6a — Signal Plumbing

### Files touched

- `ghostframe-lib/src/tile/classifier.rs`: new `AdaptationContext` struct + `set_adaptation_context` method. `set_bytes_per_us` retained as a thin shim that constructs a sparse context (default everything but `bytes_per_us`); deprecated for removal in M3.6c.
- `ghostframe-lib/src/transport/io_bridge.rs`: extends `BridgeState` with an `AdaptationContext` field + bumps `last_update_seq` from `update_fec_from_feedback` (extends the existing call site, no new poll point). Adds a new method `sample_quic_path_stats(&mut self, conn: &quinn::Connection)` called from the existing server tick.
- `ghostframe-lib/src/transport/feedback.rs`: no changes to wire format. Add a `pub fn smoothed_loss_rate(&self, history: &VecDeque<ReceiverFeedback>) -> f32` helper that the io_bridge owns history for (5-window window).
- `ghostframe-xdaemon/src/server.rs` (or whichever file holds the tick): call `bridge.sample_quic_path_stats(&conn)` once per outer loop iteration.

### Tests added in M3.6a

- `classifier::tests::adaptation_context_overrides_static_bytes_per_us` — calls `set_adaptation_context` and verifies `bytes_per_us()` returns the context value, not the default.
- `feedback::tests::smoothed_loss_rate_5_window_average` — pushes 5 feedbacks at 0%, 0%, 20%, 0%, 0% loss and asserts the 5-window mean is 4%.
- `io_bridge::tests::adaptation_context_updated_from_feedback` — extends an existing feedback dispatch test to also assert `bridge.adaptation_context.last_update_seq` incremented.

No e2e changes. No behavior changes. The classifier sees a dynamic `bytes_per_us` but still has only the M3.5 cost rule to apply it to, and at the bench-calibrated point the value matches the static default. Sweep: full e2e + lib runs as a no-regression gate.

### What M3.6a does NOT do

- Does not consume `loss_rate`, `suspended`, `smoothed_rtt_us`, or `refinement_deficit_tiles`. The fields exist in `AdaptationContext` and are populated, but `decide()` doesn't read them yet. (Avoids coupling M3.6a's review surface to M3.6b's policy debate.)

## Phase M3.6b — Policy Refactor

### Files touched

- `ghostframe-lib/src/tile/classifier.rs`: `decide()` extended with bias + override logic per "Refinement-deficit bias term" above. New constants. `hysteresis_frames` → `hysteresis_micros` field rename + default conversion. New `last_decision_signals` field on `Classifier` for telemetry hooking.
- `ghostframe-lib/src/tile/escalation.rs`: no changes (its source-codec set was already pruned in M3.5b).
- `ghostframe-lib/src/transport/scheduler.rs`: no changes. Inner-loop `refinement_bandwidth_fraction` self-adaptation is left untouched per "Architecture" note above.
- `ghostframe-lib/src/transport/io_bridge.rs`: classifier `decide()` call site no longer needs changes; the new signals are already in `AdaptationContext` after M3.6a.

### E2E tests added in M3.6b

- `e2e_bandwidth_cap_motion_degrades_to_h264` — sets `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP=250_000` (2 Mbps, bytes-per-sec), drives motion content, asserts classifier ended in H264.
- `e2e_bandwidth_cap_idle_holds_lossless` — same cap, drives 5 s idle content after 1 s motion, asserts classifier ended in TileCodec with at least 1 PixelPerfect transition.
- `e2e_loss_override_triggers_h264` — `GHOSTFRAME_INBOUND_LOSS_PROBABILITY=0.15` on idle content, asserts classifier ended in H264 within 2 s of loss injection start.
- `e2e_suspension_triggers_h264` — drives suspension signal via existing test hook, asserts classifier switched within 1 hysteresis window.

### E2E tests adjusted in M3.6b

Enumerated rather than "let's see what breaks". Each is a deliberate adjustment from "frame-count hard threshold" to "wall-clock behavioral outcome":

- `e2e_mode_switch`: assert `final_codec == TileCodec` (idle) and `peak_codec == H264` (motion) rather than counting specific frame indices.
- `e2e_codec_transition`: same shape — replace frame-index assertions with "X seconds after motion stopped, in TileCodec".
- `e2e_h264_motion`: assert "motion period yielded ≥ N H264 frames" rather than "frames 5..20 were H264".
- `e2e_progressive_refinement`: assert "PixelPerfect transition fired" + "happened within X seconds" rather than "after exactly N passes".

These are the four tests M3.5b regression-swept; M3.6b updates them in the same commit that lands the policy refactor (atomic — old asserts and old code go together).

### Lib tests in M3.6b

- `classifier::tests::refinement_bias_promotes_tilecodec_under_headroom` — constructs an `AdaptationContext` with high `bytes_per_us`, a non-empty `refinement_deficit_tiles`, and asserts `decide()` returns TileCodec where the M3.5 cost rule alone would have returned H264.
- `classifier::tests::headroom_guard_forces_h264` — sets `bytes_per_us` below `HEADROOM_MIN_BYTES_PER_US`, asserts H264.
- `classifier::tests::loss_override_forces_h264` — sets `loss_rate` above `LOSS_OVERRIDE_THRESHOLD`, asserts H264.
- `classifier::tests::suspension_forces_h264` — sets `suspended = true`, asserts H264.
- `classifier::tests::hysteresis_micros_holds_dwell` — drives a back-and-forth decision sequence within the hysteresis window, asserts dwell.
- Existing `classifier::tests::*` adjusted for `hysteresis_micros` rename. Test count + assert intent preserved.

### What M3.6b does NOT do

- Does not touch the scheduler's `refinement_bandwidth_fraction` self-adaptation.
- Does not retune the three new constants from data — those start at the values listed in "Refinement-deficit bias term" and get retuned in M3.6c.
- Does not add per-content-class policy (e.g. "text content gets a stickier refinement bias"). Spec'd as future M4+ work if M3.6c's bench shows class-dependent thrashing.

## Phase M3.6c — Tuning + Observability

### New env-var

`GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP=<bytes_per_sec>` — mirrors the existing loss-injection env-var protocol (`reference_e2e_loss_injection.md`). When set, `io_bridge` rate-limits its outbound datagram send rate to the cap. Implementation: token-bucket in `io_bridge` send path, refilled by wall-clock elapsed. Read once at session open from env; not dynamically reconfigurable.

Used by both the M3.6b e2e tests and the M3.6c bench. Production code path is the same (the cap defaults to `u64::MAX` which is a no-op token bucket).

### Bench points

Layer B (`codec_report`) scenes are re-run at three `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP` settings × 7 existing scenes = 21 runs:

| Cap | bytes_per_us | rough link |
|---|---|---|
| 1_250_000 | 1.25 | 10 Mbps DSL |
| 3_750_000 | 3.75 | 30 Mbps cable |
| 12_500_000 | 12.5 | 100 Mbps LAN (current M3.5 calibration point) |

Same metrics as M3.5b (capture→paint latency, wire bandwidth, server CPU/RSS, terminal SSIM) plus a new metric: `mode.dwell_seconds` per codec choice per scene. The matrix tells us where the policy thrashes (high mode-switch count for given scene+bandwidth) and where it lives. Constants retuned by inspection of that matrix.

### New telemetry event

`mode.decision` emitted by `Classifier::decide()` on every mode change (not every call — debounced by `last_decision`). Payload:

```json
{
  "event": "mode.decision",
  "frame_seq": 1234,
  "from": "TileCodec",
  "to": "H264",
  "reason": "loss_override",
  "bytes_per_us": 3.42,
  "smoothed_rtt_us": 18500,
  "loss_rate": 0.13,
  "suspended": false,
  "refinement_deficit_tiles": 18
}
```

`reason` is one of `{cost_comparison, headroom_guard, loss_override, suspension, hysteresis_clamp}`. Surfaces *why* the policy chose what it chose — the audit trail the bench needs for retuning and the field needs for incident triage.

Rides existing `tracing::info!` channel + bench JSON subscriber (no new wire bytes; same pattern as M3.5's `frame.captured` / `frame.last_send`).

### Bench report update

A new "M3.6 Dynamic Policy" section appended to `docs/specs/m3-codec-bench-results.md`. Two new tables:

- **Table 9 — Mode dwell × bandwidth × scene.** Cells: `(H264_seconds, TileCodec_seconds, mode_switches_count)` per (scene, bandwidth) pair. Highlights cells where switch count > 5/scene as "thrashing".
- **Table 10 — Override-trigger frequency × bandwidth.** Cells: count of `mode.decision` events grouped by `reason` per bandwidth cap. Validates that overrides fire when expected (loss override at 0% loss → 0 events; suspension override at 0 suspensions → 0 events).

Narrative: which content classes benefit most from the bias, which bandwidth points show stable PixelPerfect convergence, recommended next steps. Same shape as M3.5b's section 8.

### Constants retune commit

One commit at end of M3.6c: `tune(classifier): retune M3.6 dynamic-policy constants from bench`. Touches the three constants + the `hysteresis_micros` default. Commit message cites the table cells that drove each value. Same shape as M3.5b's CostModel retune commit.

### Regression sweep at M3.6c close-out

All of:
- `e2e_mode_switch`, `e2e_progressive_refinement`, `e2e_lossless_buildup`, `e2e_codec_transition`, `e2e_h264_motion`, `e2e_multi_tile_grid`, `e2e_solid_color`, `e2e_ack_telemetry_no_waste` — existing M3.5 sweep set, must still pass.
- `e2e_bandwidth_cap_motion_degrades_to_h264`, `e2e_bandwidth_cap_idle_holds_lossless`, `e2e_loss_override_triggers_h264`, `e2e_suspension_triggers_h264` — new in M3.6b, must still pass after the tune.
- `cargo test -p ghostframe-lib --lib` — full lib sweep.

## Wire protocol additions

**None.** Same as M3.5. All signal sources are existing channels:
- `ReceiverFeedback` — existing 22-byte format, existing 100 ms cadence, existing wire discriminator 0x01.
- QUIC `path_stats` — read-only from the quinn `Connection`, not transmitted.
- `mode.decision` telemetry — rides existing `tracing::info!` infrastructure.
- `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP` — env-var, read once at session open, not wire-transmitted.

No new datagram discriminators. No `Codec` enum changes. Existing protocol stays stable through all three phases.

## Out of scope

- **Per-tile H264 as a policy option.** Dropped in practice alongside BC1; the M3.6 toolbox is `{H264-full-frame, Solid, PalRle, Cdf53}`. Reintroducing it would be a separate milestone with its own brainstorm.
- **BC1 as a policy option.** Same — verdict per M3.5b is "drop". M3.6 does not re-litigate.
- **State-machine policy refactor.** Spec'd as M3.6d upgrade path if M3.6c bench shows thrashing the biased-cost approach cannot tune away. Not built speculatively.
- **Per-content-class policy.** No "text content gets stickier refinement bias" — the M3.6c matrix tells us whether we need it; if yes, a separate M4+ brainstorm decomposes it.
- **Adaptive `refinement_bandwidth_fraction` redesign.** Scheduler's existing inner-loop self-adaptation is left untouched. Replacing it with an RTT/loss-aware estimator is M4+ tied to §6.5.
- **Cross-hardware bench matrix.** Single dev machine for M3.6c bench, same as M3.5. The bandwidth axis (3 caps) is the new dimension; hardware axis is left for a future cross-platform milestone.
- **Production bandwidth-cap config.** `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP` is a test/bench hook. Real-world cap discovery is the network's job (QUIC cwnd); no operator-facing config landed in M3.6.
- **ReceiverFeedback wire-format extension.** No new fields. If M3.6c reveals a missing signal (e.g. "client says decoder GPU is saturated"), it lands in a separate spec.
- **Removal of `Classifier::set_bytes_per_us` shim.** Deprecated in M3.6a, removed in a follow-up cleanup after M3.6c — not in scope as a phase deliverable.

## Decision Register

| # | Decision | Rationale |
|---|---|---|
| D1 | M3.6 split into 3 phases (a: plumb, b: policy, c: tune) | Mirrors M3.3/M3.5 cadence. Each phase is one reviewable PR. Plumbing-with-no-behavior change lets the wiring be reviewed for correctness before the policy debate; policy refactor lands with new e2e tests so it's testable in isolation; tune is a single commit citing data. |
| D2 | Objective A: maximize wall-clock at PixelPerfect, graceful B-grade fallback | User-stated. Single scalar makes constants tunable from bench data. Pareto framing rejected (D3) because two-objective optimization requires a weighting choice we'd just smuggle into constants anyway. |
| D3 | Reject Pareto multi-objective policy | Equivalent to picking weights; weights become tunable constants; constants become a 1D scalar. Pareto framing adds notational ceremony without changing the engineering. |
| D4 | Signals: hybrid QUIC `path_stats` + `ReceiverFeedback` | QUIC alone misses receiver-side datagram drops (we don't retransmit datagrams); ReceiverFeedback alone undersamples between its 100 ms windows. Hybrid catches both. |
| D5 | Policy shape: refinement-deficit bias on existing cost comparison | The M3.5 cost comparison already has the right shape; bias is a targeted extension. State machine (D6) is heavier and re-validates everything. |
| D6 | State machine as D upgrade path, not initial | Spec'd as M3.6d if M3.6c bench data shows the biased-cost approach thrashes. Decision re-litigated by data, not intuition. Avoids speculative complexity. |
| D7 | Degradation triggers: headroom guard + loss override + suspension override | Three orthogonal failure modes (bandwidth, loss, suspension); each gets a dedicated hard-override path rather than being smuggled into the cost comparison. Easier to reason about, easier to test (one e2e per trigger), easier to telemeter (explicit `reason` field). |
| D8 | Hysteresis: micros not frames | Frame-count hysteresis varies 6× across the production fps range (60 → 10 fps idle). Wall-clock dwell is the user-experience metric. One-time rename + default conversion is cheap. |
| D9 | No per-content-class policy in M3.6 | M3.6c bench will tell us if we need it. Speculative class-conditional rules pre-tune without data. |
| D10 | Cold start unchanged (still H264 first via cost comparison) | Already correct. QUIC slow-start + empty `AdaptationContext` naturally biases toward H264 until the link warms up. No explicit warm-up timer needed. |
| D11 | E2E tests get rewritten in same commit as policy refactor (M3.6b) | Old frame-count assertions and the policy that satisfied them go together. Atomic commit means git bisect doesn't land on a half-state. Adjusted-test list enumerated up-front (not "let's see what breaks"). |
| D12 | New env-var `GHOSTFRAME_OUTBOUND_BANDWIDTH_CAP` mirrors loss-injection protocol | Existing pattern is good. Token-bucket in io_bridge send path is minimal new code. Cap defaults to no-op so production code path is unaffected. |
| D13 | Bench at 3 bandwidth points (10 / 30 / 100 Mbps) × 7 existing scenes | Three points span DSL → cable → LAN; existing scenes give content coverage. 21 runs is tractable for a single bench session. |

| D15 | `AdaptationContext` fields populated in M3.6a but unused until M3.6b | Decouples plumbing review from policy debate. Compiles cleanly in M3.6a; behavior changes only when M3.6b's `decide()` reads the new fields. |
| D16 | `set_bytes_per_us` retained as shim in M3.6a, deprecated for later removal | Backward-compat for existing M3.5 callers/tests during the M3.6a window. Cleanup deferred so M3.6 phases stay small. |
| D17 | Initial constants set by intuition; retuned by data in M3.6c | M3.6b lands runnable code; M3.6c tells us the right numbers. Same pattern as M3.5b's CostModel retune commit. |
