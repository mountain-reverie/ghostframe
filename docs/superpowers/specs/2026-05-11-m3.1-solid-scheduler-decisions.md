## Purpose

The umbrella M3 design (decision D11) declares M3.1 ready for writing-plans without a further per-codec brainstorm — the architectural design is complete there. This addendum captures only the **five implementation decisions** taken in the M3.1 kickoff session that are not pinned down by the umbrella. It is not a full design; it is a delta. The umbrella remains the source of truth for everything else (scheduler API shape, ACK datagram format, wire protocol, web-client integration, codec abstraction, testing layers).

Read this addendum together with umbrella §M3.1.

## Decisions

### D1 — Classifier remains sentinel-gated; Solid is plumbing-only in M3.1

The classifier rule `unique_colors == 1 ⇒ CodecState::Solid` requires the `unique_colors` metric, which M3.0 populates as the sentinel `u16::MAX` because the backing GPU-compute pass does not land until M3.3 (umbrella §M3.0 "M3.0 sentinel policy", D16).

M3.1 does **not** add a CPU-side `unique_colors == 1` scan to make Solid fire end-to-end under real content. The Solid encoder, the scheduler, the ACK protocol, the retry loop, and the web-client decode path all ship and are exercised by unit tests that inject `TileMetrics { unique_colors: 1, .. }` directly. The E2E test `e2e_solid_color` asserts the *plumbing* (4-byte payload, `Codec::Solid` discriminant on the wire, render correctness, loss tolerance via retries) by forcing the classifier state in test setup, not by relying on real-content classification.

**Why:** The CPU scan would be a 1024-pixel pass per dirty tile that becomes dead code the moment GPU compute lands in M3.3. M3.1 is the infrastructure phase; faking up real Solid selection just to demo the codec end-to-end is the wrong tradeoff. Real Solid firing on real content arrives naturally with M3.3.

### D2 — Inbound ACK datagrams routed via a new WebTransport datagram-receive intake

Server-side intake for ACK_BATCH_MSG_TYPE (`0x02`) datagrams is a new path. The existing `ReceiverFeedback` flow uses a reliable bidi stream (`transport/webtransport.rs:71`, `transport/io_bridge.rs:907-930`) and is unrelated. M3.1 adds:

- An inbound-datagram callback on `WebTransport` sessions that inspects the first byte.
- Datagrams with `[0] == 0x02` route to `Scheduler::on_ack` after parsing.
- Anything else falls through to existing handlers (none today, but the structure stays open).

**Why:** The umbrella specifies datagram-not-stream for ACKs (D6) because lost ACKs are harmless and `ReceiverFeedback`'s 100 ms reliable-stream cadence is too slow for ACK-driven retry.

### D3 — CPU path goes through the same scheduler as GPU path

`process_frame_cpu` (`transport/io_bridge.rs:335-398`) currently emits `Codec::Raw` tiles directly via `fragment_tile`. M3.1 routes both `process_frame_cpu` and `process_frame_gpu`'s `FrameMode::TileCodec` branch through `Scheduler::enqueue` → `Scheduler::tick` → `fragment_tile`. The CPU path classifies tiles using the same `Classifier` and emits `Codec::Raw` until classifier rules fire — which, given D1, means always-Raw in M3.1.

**Why:** Uniform codec dispatch is cheaper than maintaining two parallel emission paths. The cost is one shared scheduler call site; the benefit is that every M3.2+ codec lands once and works on both paths automatically.

**Caveat:** This supersedes umbrella decision D13 ("M3.0 CPU path stays in tile-codec-Raw mode") in spirit by moving CPU emission through the scheduler. CPU path *output* still stays `Codec::Raw` in M3.1; only the dispatch mechanism changes. Full-frame H.264 on the CPU path is still out of scope per umbrella Future Work #7.

### D4 — `Scheduler::tick` ships with placeholder unlimited budget; real budgeting waits for M3.3

`Scheduler::tick(budget_bytes: usize)` exists in the API signature per umbrella §M3.1, but M3.1 hardcodes the call site to `usize::MAX` (or equivalent). No bandwidth estimator, no `refinement_bandwidth_fraction`, no high-priority vs refinement partitioning. The real gate in M3.1 is QUIC's datagram send buffer + congestion controller.

**Why:** Budgeting only earns its keep under priority tension (new dirty tiles vs refinement bit-planes), which doesn't exist until M3.3's CDF 5/3 passes compete with fresh tiles for bandwidth. Wiring budgeting earlier means inventing a problem to test it against. The `budget_bytes` parameter stays in the API so M3.3 wires real numbers through it as a one-call change.

Tracked in memory at `project_m31_deferred_budget.md` so it isn't forgotten when M3.3 starts.

### D5 — Deterministic loss injection via a feature-gated drop hook

The codebase has no existing drop hook (verified: only observed loss via `ReceiverFeedback.datagrams_lost`; spec §1487 mentions `tc`/`netem`/`turmoil` as future ideas, none wired). M3.1 needs loss injection for `e2e_solid_color` (5% outbound drop to exercise retries) and `e2e_ack_loss` (100% inbound `0x02` drop for 2 s to exercise the no-retry-storm property).

**Mechanism:**
- Feature flag `test-loss-injection` (also enabled under `cfg(test)`).
- `IoBridge` holds an optional `LossInjector { drop_probability: f32, drop_pattern: Predicate, rng: SeededRng }` for the outbound side, applied at `transport/io_bridge.rs:232` (`send_to_all_sessions`).
- A parallel inbound drop hook applied at the new ACK-intake path from D2, scoped by the same `drop_pattern` (so tests can drop only `[0] == 0x02` datagrams).
- Seeded RNG ⇒ deterministic in CI. Predicate keyed on first byte for cheap matching.
- Compiled out in release builds.

**Why this over `tc netem`:** No NET_ADMIN capability juggling, no container reconfiguration, deterministic across runs, no host-side state to clean up, runs identically on any developer machine.

## What this addendum does NOT change from the umbrella

For reference, all of the following stay as specified in umbrella §M3.1:

- `encoder/solid.rs` API: `encode_solid(tile) -> [u8; 4]`, `decode_solid(payload) -> Result<[u8; 4], _>`.
- `transport/scheduler.rs` types: `WorkState`, `TileWork`, `Scheduler` with `enqueue` / `bump_generation` / `tick` / `on_ack`.
- Round-robin tick semantics, 2 × RTT retry, gen-bump cancels in-flight, 16-generation wrap.
- ACK datagram format: 1 + 1 + count × 4 bytes; ≤258 B; one unreliable datagram per flush.
- `TileHeader` byte `[3]` becomes `(gen: u4 << 4) | (pass: u4)`. M2 sites continue to set `gen=0` and now implicitly `pass=0`.
- Web client: `ack.ts` (`AckBatcher` flushing on ≥64 entries OR ≥5 ms), Solid decode in `decoder.ts`, `drawSolidTile` via `ctx.fillStyle` / `ctx.fillRect` in `renderer.ts`.
- Proptest C3 (`unique_colors == 1 ⇒ CodecState::Solid`) re-enabled at `tile/tests_proptest.rs:434`.
- E2E coverage: extend `e2e_solid_color`, add `e2e_ack_loss`.
- Out-of-scope: PalRLE/BC1/CDF53 encoders, multi-pass scheduling, refinement-bandwidth adaptation.

## Post-merge status (2026-05-11)

Tasks 1–17 from the plan shipped as designed. Final review surfaced one Blocking finding (B1) and three Nits, all fixed before merge. Two follow-up tasks were added to close gaps the umbrella's E2E gates ambitiously listed but the M3.1 unit scope hadn't covered:

### Task 18 — Scheduler-dispatch helper + `fragment_tile` signature cleanup

`process_frame_cpu` and `process_frame_gpu`'s TileCodec branch were duplicating the grid-sync → RTT update → bump+encode+enqueue → tick → fragment+send pipeline. Extracted into `IoBridge::dispatch_dirty_tiles_via_scheduler(...)` taking a `SchedulerEmissionPolicy::{CpuRawOnly, GpuClassifierDriven}` enum. `fragment_tile` now takes `(generation, pass)` parameters directly; the post-hoc byte-patch trick (`dg[DATAGRAM_HEADER_SIZE + 3] = ...`) is gone. Adds two unit tests (`dispatch_via_scheduler_cpu_policy_enqueues_raw_tiles`, `dispatch_via_scheduler_gpu_policy_emits_solid_for_solid_state`) — the CPU-path scheduler integration is unit-testable now without a connected WebTransport session.

### Task 19 — E2E loss-injection wiring

`IoBridge::loss_injector_from_env(direction)` reads `GHOSTFRAME_<OUTBOUND|INBOUND>_LOSS_{PROBABILITY,PREDICATE,SEED}` and installs the cfg-gated `LossInjector` at production-constructor time. The test-server Dockerfile builds with `--features ghostframe-lib/test-loss-injection`. `setup_e2e_with_env` (pre-existing) carries the env vars to the container.

Two new E2E tests:
- `e2e_solid_color_5pct_loss` — 5% outbound tile-datagram drop, 7 s wait, asserts canvas still renders red via 2×RTT retransmits.
- `e2e_ack_loss` (un-ignored from Task 16 scaffold) — 100% inbound ACK drop, 5 s wait, asserts system survives without panic and renders red.

### Bundled fixes (pre-existing bugs uncovered)

The Task 15+16 commit (`0657759`) also fixed two non-M3.1 bugs that blocked the E2E baseline: `ghostframe-xdaemon/src/drm_capture.rs` `OnceLock` panic → `Err` so the X11 fallback path is reachable; `tests/containers/test-server/entrypoint.sh` VKMS auto-detect now requires `/dev/dri/card0` in the container (not just the host sysfs entry). These should ideally have been a separate PR; documented here for git-archeology purposes.

### What's still deferred

- **Dynamic loss-config toggle** — current env-var protocol is static per server lifetime. A "drop ACKs for 2 s then resume" pattern needs a reliable-bidi control message (M3.5 or as needed).
- **Server-side scheduler observability** — `e2e_ack_loss` verifies "system survives" but doesn't directly observe `Scheduler::queue_len()` bounds. Adding a `__ghostframeScheduler` tracing stat is a small follow-up.
- **Real budget in `Scheduler::tick`** — still `usize::MAX` placeholder per D4. Lands with M3.3.
- **Real `Codec::Solid` firing** — still gated by the `unique_colors` sentinel per D1. Lands with M3.3 GPU compute.
