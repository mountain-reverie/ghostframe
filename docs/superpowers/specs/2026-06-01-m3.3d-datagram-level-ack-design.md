# M3.3d — Datagram-level ACK protocol

**Date:** 2026-06-01
**Status:** approved, ready for implementation plan
**Prerequisite:** M3.3c merged (depends on `cdf53_passes_acked`, PixelPerfect transition sweep, `cdf53.pixelperfect` log line).

## Problem

M3.3c added a PixelPerfect transition (server → "this tile is fully refined, stop re-emitting") driven by per-pass ACKs from the client. Investigation during pre-merge review (see `project_m33c_complete.md`) found the transition never fires in real e2e despite the existing `AckBatcher` plumbing being correct.

Root causes:

1. **Wasted ACKs.** Client `ackBatcher.add(...)` (main.ts:523) fires for every tile of every codec — including Solid, PalRle, Raw, H264, which have no `cdf53_in_flight` entry server-side. Empirically 60-100% of ACKs MISS, producing log noise and bandwidth waste, and obscuring real Cdf53 delivery signal.
2. **`bump_generation` wipes the counter.** Every motion-phase frame calls `bump_generation_collecting` for every dirty tile (io_bridge.rs:617), which retains-out both `cdf53_in_flight` AND `cdf53_passes_acked` for that tile across all generations (scheduler.rs:203-205). Under typical motion-static cycles the ACK round-trip (~1 s with the current 5 ms batch interval × 157 batches) loses races with motion bumps, and the counter never reaches 14.
3. **Tile-level ACK semantics are wrong.** A tile is meaningless from a transport perspective; a datagram is what's actually lost or received. Per-tile ACKs are a leaky abstraction over per-datagram delivery.

## Goal

Replace the per-tile ACK wire protocol with a per-datagram ACK protocol. Server tracks at emit time which tiles each datagram covers; client ACKs each received datagram by `(frame_seq, frag_idx)`; server reconstructs per-tile delivery from the coverage map.

**Acceptance:**
- `e2e_cdf53_lossless_buildup` shows `cdf53.pixelperfect` log lines (count ≈ tile count of the gradient pattern).
- `e2e_progressive_refinement` shows ≥ 1 PixelPerfect transition during the 7 s settle window.
- Server logs show `cdf53_ack_miss` count drops to ~0 under steady-state TileCodec.
- All existing M3.3 e2e tests still pass.

## Architecture

```
┌──────────────────────────────────────────────────────────┐
│  SERVER                                                  │
│                                                          │
│  emit datagram ─┬─→ recent_frame_fragments (bytes)       │
│                 │   (existing; LRU 200 for NACK retx)    │
│                 └─→ fragment_coverage (tile list)        │
│                     (NEW; bounded LRU per-session)       │
│                                                          │
│  ack rx ──→ for (frame_seq, frag) in batch:              │
│               coverage.take((seq, frag))                 │
│               for each entry in coverage:                │
│                 codec-specific delivery bookkeeping      │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│  CLIENT                                                  │
│                                                          │
│  datagram rx ──→ ackBatcher.add({frameSeq, fragIdx})     │
│                  (every received datagram, all codecs;   │
│                   fires BEFORE fragment-assembly path)   │
└──────────────────────────────────────────────────────────┘
```

## Wire format

`AckBatch` (`transport/ack.rs`):

```
[0]      message_type = 0x03   (was 0x02; bumped to fail loud on mid-rollout)
[1]      count: u8 (1..=64)
[2..]    count × 6 bytes:
            [0..4]  frame_seq: u32 little-endian
            [4..6]  frag_idx:  u16 little-endian
```

Max datagram size: `2 + 64 × 6 = 386` bytes, well under MTU.

The pre-release project status (no clients in the wild) means the wire break does not require version negotiation, a HELLO capability bit, or a dual-path fallback. The message-type bump from `0x02` to `0x03` is purely defensive: a stale dev binary mid-rollout fails with `AckDecodeError::WrongMsgType(0x02)` rather than silently mis-parsing as the new layout.

## Coverage map

```rust
// ghostframe-lib/src/transport/fragment_coverage.rs (new module)

#[derive(Clone, Copy, Debug)]
pub struct FragmentCoverage {
    pub tile_x: u8,
    pub tile_y: u8,
    pub generation: u8,
    pub pass_idx: u8,           // 0 for non-Cdf53 codecs (sentinel)
    pub codec: Codec,
    pub palette_id: Option<u8>, // Some(_) only for PalRle; drives palette_delivered tracking
}

pub struct FragmentCoverageMap {
    // LRU-bounded map (u32 frame_seq + u16 frag_idx) -> coverage list.
    // Implementation choice between the `lru` crate and a manual
    // VecDeque + HashMap is an impl-plan detail; either works.
    // Values use SmallVec to inline up to 8 coverage entries without
    // heap allocation (covers typical bundled-PalRle and single-pass
    // Cdf53 cases). SmallVec is already a transitive dep; needs to be
    // promoted to a direct dep in ghostframe-lib/Cargo.toml.
    ...
}

impl FragmentCoverageMap {
    pub fn new(capacity: usize) -> Self { ... }
    pub fn record(&mut self, key: (u32, u16), coverage: SmallVec<[FragmentCoverage; 8]>);
    pub fn take(&mut self, key: (u32, u16)) -> Option<SmallVec<[FragmentCoverage; 8]>>;
}

/// Starting heuristic sized for 1920×1080 @ 30 fps × 1 s ACK round-trip
/// × ~10% headroom. TODO(m3.3e): make this a function of (cols × rows ×
/// capture_fps × rtt_budget) instead of a fixed const; at 4K @ 60 fps the
/// in-flight worst case grows ~4× and 5000 will be insufficient.
pub const FRAGMENT_COVERAGE_CAPACITY: usize = 5000;
```

**New direct dependencies**: `smallvec` (transitive today, promote to direct). The LRU backing can be the `lru` crate or a manual `VecDeque<(K, V)> + HashMap<K, usize>` — impl plan picks.

**Storage**: per-connection. Lives in `WtSession` or alongside `recent_frame_fragments`. Multi-client clarity + no cross-client interference.

**Eviction**: pure LRU. Evicted entries are equivalent to "ACK never arrived" — no special handling. The tile stays in its current `codec_state` and re-emits on the next dirty cycle, same as today's lost-ACK path.

**Cost**: `SmallVec<[FragmentCoverage; 8]>` inlines up to 8 entries (covers the typical bundled-PalRle and single-pass-Cdf53 cases without heap allocation). Each `FragmentCoverage` is ~8 bytes. 5000 entries × 8 bytes × 8 (inline avg) ≈ 320 KB per active client.

**Independence from `recent_frame_fragments`**: the two have different lifetime semantics. `recent_frame_fragments` retains bytes for RTT-bounded NACK retransmission (200 entries). `fragment_coverage` retains tile metadata until ACK or session end (5000 entries). Conflating them landed M3.3c in the wasted-ACK-MISS mess; keeping them separate makes per-purpose tuning straightforward.

## Per-codec ACK semantics

What `dispatch_ack_datagram` does for each codec when a coverage entry ACKs:

| Codec   | ACK action                                                                                         | Reason                                                                                       |
|---------|----------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| Cdf53   | `scheduler.cdf53_passes_acked[(tile, gen)] += 1` (existing per-pass increment)                     | Drives `tile_fully_acked` → `PixelPerfect` transition.                                       |
| PalRle  | If `palette_id.is_some()` and not yet `delivered`: `palette_table.delivered.insert(pid)`, decrement `in_flight_carrying[pid]`, release ref. (existing logic, moved here from `Scheduler::on_ack`.) | Drives `PaletteTable` LRU correctness for FreeButCached transitions.                         |
| Solid   | No-op (delivery telemetry only).                                                                   | Solid has no terminal state and no palette.                                                  |
| Raw     | No-op.                                                                                             | Same as Solid.                                                                               |
| H264    | No-op.                                                                                             | Frame-level codec; tile-level ACK doesn't change H264 decoder state.                         |

**`cdf53_in_flight` is removed.** Its only purpose was to detect "is this Cdf53 ACK for an entry the queue drained at emit time" — that question is now answered by the coverage map directly. `cdf53_passes_acked` stays (PixelPerfect signal).

**`Scheduler::on_ack` decomposes into two narrower methods.** Today it does two things mixed together: (1) flips a `TileWork`'s `WorkState::Acked` and prunes from `priority_queue` / `refinement_queue`, and (2) updates `cdf53_passes_acked` / `cdf53_in_flight`. Under the new design (1) is irrelevant (the new flow doesn't look up tiles by `(tile, gen, pass)` in the queue — coverage tells us directly what the datagram contained) and (2) collapses to the Cdf53 counter increment.

Split into:
- `Scheduler::record_cdf53_ack(tile_x, tile_y, generation)` — increments the per-(tile, gen) counter. Called from the coverage-ACK handler for Cdf53 entries.
- The PalRle-on-ack bookkeeping moves out of `Scheduler` entirely (into `dispatch_ack_datagram`'s PalRle branch, operating on `palette_table` directly — same data, cleaner ownership).

Delete `Scheduler::on_ack` and `Scheduler::cdf53_in_flight` entirely. The unit tests that exercise queue-state-flip semantics (`dispatch_ack_datagram_clears_in_flight_work` et al.) are rewritten to exercise the new coverage-ACK path end-to-end.

**`Scheduler::pending_refinement_snapshot`** (the `cdf53-diag` snapshot used by `e2e_refinement_cancel`): currently merges `refinement_queue` (Pending) + `cdf53_in_flight` (InFlight-but-removed-from-queue). With `cdf53_in_flight` gone, the snapshot reads from `refinement_queue` + outstanding `fragment_coverage` entries that carry `Codec::Cdf53` and haven't been ACKed.

## Fragmented payload handling

When the server emits a tile payload spanning N datagrams (e.g., a large PalRle index buffer, or a Cdf53 pass over MTU), only the **final fragment's** coverage entry carries the tile's `FragmentCoverage`. The N − 1 earlier fragments record an empty coverage list (or get no coverage entry at all — same effect).

**Rationale**: client can't usefully process the tile until all fragments arrive and assembly succeeds. ACKing intermediate fragments would be "I received bytes 0-1199" — meaningless for delivery semantics. ACKing only the final fragment means "the tile's complete payload is now on the client".

**Loss model**:
- Lose any non-final fragment → assembly never completes → client never ACKs the final → tile counter stays unchanged → tile stays in re-emit state. ✓
- Lose the final fragment → same outcome. ✓
- Lose the ACK datagram → coverage entry never gets removed; eventually evicted by LRU. Same outcome as today's lost-ACK path. ✓

**Bundled small tiles** (typical PalRle/Solid case): a single datagram packing K complete tiles is K "final fragments" packed together. Its coverage list has K entries. One ACK = K delivery confirmations. The common case works without special-casing.

**Server side**: the dispatcher already knows when it's writing the last fragment of a payload (it's the one with the "complete tile" header bit set). At that point, push the tile's `FragmentCoverage` into the coverage list for that datagram. Earlier fragments contribute nothing.

**Client-side assembly is independent of ACK**: today the client only calls `ackBatcher.add(...)` after `frameAssembly` completes (main.ts:523, post-dispatch). Under the new design, ACK fires per-datagram on receipt, BEFORE the assembler runs. The two paths run concurrently per fragment: (1) "ACK this datagram immediately", (2) "feed bytes to assembler, dispatch tile when complete". They don't depend on each other.

**Prevalidate failure interaction**: if Cdf53 prevalidate fails (`main.ts:494`, `r.ok = false`), the client today still calls `ackBatcher.add(...)` and the server thinks the tile was delivered. Under the new design the client ACKs on RECEIPT (before prevalidate), so the situation is the same: server gets "datagram delivered" (true) + separately gets the decode-error report via the existing feedback path. The two signals stay independent. **Decision: accept this** — prevalidate failures are wire-level corruption that decode-error feedback already handles; ACKing receipt is honest signal.

## Migration plan

1. Add `fragment_coverage` module + populate at emit site (server).
2. Bump `ACK_BATCH_MSG_TYPE` from `0x02` to `0x03`.
3. Replace `dispatch_ack_datagram` body with the coverage-lookup loop.
4. Delete `Scheduler::on_ack` and `Scheduler::cdf53_in_flight`. Add `Scheduler::record_cdf53_ack`. Move PalRle-on-ack bookkeeping out of `Scheduler` into `dispatch_ack_datagram`'s PalRle branch.
5. Rewrite `pending_refinement_snapshot` source-of-truth.
6. Rewrite client `AckBatcher` (drop tile fields, add frame_seq/frag_idx). Move `ackBatcher.add` from `main.ts:523` to the per-datagram receive site above the fragment-assembly path.
7. Cut both at once — no flag, no dual-path. Pre-release status permits the wire break without compatibility shims.

## Testing strategy

### Unit (Rust)

- `fragment_coverage::tests::lru_eviction_drops_oldest` — fill to capacity + 1, oldest is gone.
- `fragment_coverage::tests::take_returns_and_removes` — record + take + take returns None.
- `dispatch_ack_datagram::cdf53_increments_passes_acked` — coverage entry + ack → counter == 1.
- `dispatch_ack_datagram::palrle_marks_palette_delivered` — coverage with `palette_id: Some(7)` + ack → `palette_table.delivered.contains(7)`.
- `dispatch_ack_datagram::solid_is_noop` — coverage with `Codec::Solid` + ack → no state change.
- `dispatch_ack_datagram::bundled_acks_all_tiles_in_one_message` — coverage with 8 tiles in one frag → 1 ack increments 8 counters.
- `dispatch_ack_datagram::missing_coverage_is_noop` — ack a `(seq, frag)` not in coverage → no panic, no state change.
- `pending_refinement_snapshot::reads_from_queue_plus_coverage` — replaces the existing `cdf53_in_flight`-based test.

### Unit (TypeScript)

- `ack.test.ts::encodes_frame_seq_and_frag_idx_little_endian` — exact byte layout.
- `ack.test.ts::flushes_at_max_entries` — push 64 → immediate flush.
- `ack.test.ts::flushes_after_interval` — push 1 → wait 5 ms → flush.
- `ack.test.ts::msg_type_0x03` — first byte assertion (catches accidental old-format build).

### E2E

- `e2e_cdf53_lossless_buildup` — extend with PixelPerfect assertion. `--gradient --drm-direct` has no motion bump → all 14 ACKs land → counter hits 14 → `cdf53.pixelperfect` lines fire. Assert count > 0.
- `e2e_progressive_refinement` — keep pairwise-SSIM stability. Add PixelPerfect-count assertion (count > 0 within the 7 s settle window — reachable now that ACK volume is way down).
- `e2e_refinement_cancel` — verify the rewritten `pending_refinement_snapshot` still produces a non-empty BEFORE snapshot. Semantic unchanged; storage moved.
- `e2e_mode_switch` — unaffected (ACK volume change doesn't shift F/T phase labels).
- **New**: `e2e_ack_telemetry_no_waste` — drive `--solid-per-tile`, capture server logs, assert `ack_batch_received > 0` AND "tile ACK matched" count ≤ `ack_batch_received × MAX_BUNDLE_SIZE`. Catches regressions of the wasted-ACK pattern.

## Out of scope (deferred to follow-ups)

- **Dynamic coverage map sizing** based on resolution × fps. `pub const FRAGMENT_COVERAGE_CAPACITY = 5000` with a `TODO(m3.3e)` comment.
- **Refinement retransmit on loss** (I4 from the M3.3c pre-merge review): `drain_refinement_pass_major` still removes entries from queue at emit time with no InFlight-retry analogue. Lost-but-not-ACKed Cdf53 passes still strand the tile under sustained loss. Same problem space as datagram-level ACK but distinct: addresses the "what if the server's datagram never arrives" case, while M3.3d addresses "what if the ACK protocol itself is mis-modeled".
- **Multi-client ACK collation**: each connection has its own coverage map. If we ever multicast, the server would need to aggregate per-tile delivery across clients before triggering PixelPerfect. Not relevant for M3.3d.
