# --- Category 2: software-H.264-decode-too-slow-on-2-vCPU-runners ----------
# Tests whose assertions assume the WebCodecs H.264 decoder keeps up with a
# 30fps live stream within ~2s. GitHub-hosted ubuntu-24.04 runners have 2
# vCPU + 7 GB RAM, no real GPU; Chrome's software H.264 decode (via the
# ffmpeg fork bundled with Google Chrome) can't keep pace with the
# server-side x264 encoder, so by the time the test reads the canvas the
# decoder is showing the first frame both times — assertion sees
# `snap_a == snap_b` and fails.
#
# Probe diagnostics confirmed: Chrome 148 stable on the runner does support
# H.264 baseline/main/high + WebCodecs.VideoDecoder when served over
# http://localhost (cf. .github/workflows/e2e.yml's "Probe Chromium codec
# support" step and tests/chromium_probe.rs). The remaining gap is purely a
# runner-throughput limitation.
#
# These run locally on any machine fast enough to keep up with a real video
# pipeline (= every developer machine ghostframe targets).
e2e_h264_motion
e2e_h264_ssim_golden
e2e_multi_pattern

# --- Category 3: Firefox software-WebGPU mapAsync too slow on 2-vCPU runners
# Firefox tests whose bodies repeatedly call `await window.__readPixel(x, y)`
# in pixel-scan loops. Each call does a `GPUBuffer.mapAsync()` staging
# readback; on Firefox Nightly's software WebGPU backend (no real GPU on
# GitHub-hosted runners) each readback costs ~100 ms — easily exceeding
# marionette's script timeout for the 15×20 = 300-iteration scans, and
# leaving the page stuck at status="Connected" because the SolidPipeline /
# tile-renderer never produces a frame quickly enough to flip
# `firstTileRendered`.
#
# The corresponding `_chromium` variants pass — Chrome's `--use-vulkan`
# (even on llvmpipe fallback) is materially faster than Firefox's WebGPU
# CPU backend at the staging-readback path.
#
# These will unblock once either: (a) CI gains GPU passthrough for the
# Firefox-host process; (b) Firefox's software WebGPU mapAsync becomes
# competitive; or (c) we wire `__readPixelRect` into these test bodies to
# replace per-pixel readbacks with one staging-buffer copy per scan.
e2e_solid_color_firefox
e2e_edge_tiles_firefox

# --- Category 4: Firefox WebGPU page-startup is flaky on 2-vCPU runners ----
# Firefox tests whose bodies are NOT pixel-scan heavy (Category 3) but still
# fail on the GH-runner because Firefox Nightly's software WebGPU init
# sometimes drops the marionette WebDriver connection during page-startup
# with `webdriver returned error: Failed to decode response from marionette`,
# typically while the test is still inside `wait_for_frames`. The matching
# `_chromium` variant covers the actual assertion; the Firefox variant runs
# locally on dev boxes where a real GPU is present.
e2e_input_forwarding_firefox
